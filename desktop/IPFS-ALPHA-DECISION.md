# NODEX Alpha 1 — решение по IPFS runtime

Дата решения: 2026-11-11
Статус: принято для закрытой Alpha; пересмотр обязательно до публичной Beta.

## Решение

- Использовать **Kubo 0.43.1** как закреплённый IPFS runtime для закрытой Windows Alpha 1.
- Не обновлять Kubo автоматически. Версия проверяется preflight-проверкой и SHA-256 из `assets/RUNTIME-MANIFEST.json`.
- Запускать Kubo отдельным `ipfs.exe` процессом, управляемым Electron service manager.
- Хранить IPFS repo в `%APPDATA%\\NODEX\\ipfs-repo`.
- API и Gateway слушают только `127.0.0.1`; Kubo RPC API не публикуется в LAN и не проксируется напрямую на Android.
- PostgreSQL и Kubo поставляются как отдельные Windows runtime-компоненты. Docker и docker-compose не являются частью Alpha deployment.

## Почему это допустимо только для закрытой Alpha

Релиз Kubo v0.43.1 опубликован 15 сентября 2026 года. Официальные заметки указывают, что это последний Kubo от Shipyard, а инженерная и эксплуатационная работа Shipyard над IPFS завершилась 30 сентября 2026 года. Это означает отсутствие дальнейшего сопровождения со стороны этой команды, а не прекращение работоспособности протокола или автоматическое появление уязвимостей.

Alpha ограничена контролируемым кругом тестировщиков и изолированным локальным узлом. Поэтому допускается временное использование закреплённой версии при условии отсутствия автоматического публичного доступа к Kubo RPC и запрета на публичный релиз без повторной оценки поддержки и безопасности.

## Условия допуска

1. Только закрытая Alpha; не позиционировать Kubo 0.43.1 как поддерживаемую production-зависимость.
2. Проверять SHA-256 и происхождение официального Windows x64 архива до включения бинарника в дистрибутив.
3. Проверять фактическую версию `ipfs.exe` при preflight и каждом запуске.
4. Не открывать TCP 5001 или 8080 на LAN-интерфейсах; проверять bind адреса после запуска.
5. Не разрешать Android-клиенту выполнять произвольные Kubo RPC команды. Будущий LAN proxy должен иметь отдельный allowlist и авторизацию.
6. До публичной Beta провести повторный security review, проверить наличие поддерживаемого форка/преемника, план обновлений, совместимость datastore и миграцию существующего repo.

## План IPFS portability / миграции

Не обещать заранее миграцию именно на Helia: Shipyard также перечислила Helia и Boxo среди проектов, для которых прекращается её выделенное сопровождение. Helia остаётся кандидатом для технического прототипа, но не считается автоматически поддерживаемой заменой.

До публичной Beta:

1. Выделить в NODEX отдельный IPFS adapter с минимальным контрактом операций: add encrypted object, cat by CID, pin add/remove, inspect pin/status, repo health.
2. Сохранить CID и формат зашифрованных объектов независимыми от конкретного IPFS runtime. Не менять форматы NODEX и криптографию в рамках миграционного прототипа.
3. Сравнить поддерживаемый Kubo fork/continuation, Helia и иные активные реализации по maintenance ownership, security response, Windows packaging, Bitswap/libp2p interoperability, datastore import/export, pinning и производительности.
4. Отдельно проверить Helia interoperability с текущими Kubo узлами; не предполагать полную совместимость только на основании использования IPFS-протоколов.
5. Провести тесты миграции на копии репозитория: сохранность CID, чтение всех объектов, pins, восстановление после сбоя и rollback.
6. Принять отдельное архитектурное решение перед переключением runtime. Не переписывать IPFS слой одновременно с текущей стабилизацией Alpha.

## Docker

Docker Compose не используется в выбранной Windows Alpha архитектуре. Старый `secure-disk-backend/docker-compose.yml` ссылался на PostgreSQL 16 и тестовые учётные данные, не соответствующие выбранной конфигурации PostgreSQL 17.11. Он удалён как устаревший и потенциально вводящий в заблуждение deployment-файл. Миграции БД и схема backend не менялись.
